# Native 玩法实践与实测记录（2026-09-05）

## 这次实践说明了什么

“保留玩法、由 Player 简化表现”的方向仍值得继续。简单卡的表单可以完整接管；复杂卡中，开局选项、持久变量、有限关系阶段和每幕资料也能进入同一套原生能力。

这不是任意社区卡的兼容性证明。当前仍由工程师审计原卡、填写与原件哈希绑定的适配 JSON。两张复杂卡均保留 PARTIAL 报告，动态世界书规则、任意脚本、EJS 条件执行、远程 CG 等缺口仍然存在。真实聊天样本只证明本次场景跑通，不证明长剧情、所有分支或模型稳定性。

## 原卡规则与原生接管的关系

医生卡原本就是“HTML 表单 → 拼接预约文本 → 发送”的设计，没有持久变量协议。本次接管保留五项输入、多选合并、空值文案和草稿结构；没有额外要求模型输出状态。

复杂卡原本已经通过提示词约定变量更新块，再由宿主脚本处理。本次保留这层写作约定，以精确路径白名单把旧格式读入 Conversation State；状态只读宏也从这份本地状态重建。提示词负责叙事与剧情判断，Player 负责类型、写入权限、原子提交、数值范围、阶段判定和历史检查点。

因此，接管 JS/HTML 需要先区分显示、确定性计算、对话状态和宿主行为。把所有规则继续塞进提示词，或者只摘出几个数字，都会丢失原来的玩法。

## 本次交付

- 严格、原子的状态块解码；主回复与独立状态确认采用同一校验。畸形块不再吞掉尾部正文，最终投影不会重复执行有副作用的宏。
- 一次性开局提交：字段、选项常量、初始状态、世界书覆盖、草稿与提交标记一起保存；先落盘，再展示成功。开场候选、重试与重新读取保留选择。
- 草稿持久化；切换对话先完成当前保存；取消生成也保存已产生的正文；最终保存后才释放发送入口。
- 统一的暖色中性背景与青绿色强调、紧凑选择项、输入框上方状态摘要和详情面板。
- 有界数值、有限字符串选项、阈值阶段与可选布尔剧情锁。派生阶段不能由模型或开局表单直接写入。
- 每条消息的固定资料面板。历史资料来自原始消息，不被当前状态覆盖；无法完整识别时保留原文。
- 角色详情的严格适配 JSON 导入，以及三张真实卡的开发夹具。生产实现没有按角色名或源文件名分支。
- 无正文回复不执行状态补写；思考内容不会充当故事或状态证据。

运行契约见 [adaptation-runtime-v1.md](adaptation-runtime-v1.md)。

## 实测记录

本机证据存放在忽略的 `app/build/native-gameplay-verification/`。每次运行单独保存对话、正文和截图；加入响应观察器后的运行还保存仅含响应正文的 SSE，以便区分模型输出与解析问题。

- `1788577501106`：Pro 完成医生卡两轮与魔法少女卡一轮。最后一项磁盘比较抢在异步保存前执行，整条测试失败；不能记作完整通过。
- `1788579038384`：Pro 再次完成上述三轮。预约内容进入正文，开局身体保留，战局为“无战斗”、变身为“未变身”，磁盘恢复一致。脚本随后错误地向 Activity 派发返回，退出测试页面；已通过拆分独立用例修正。
- `1788579727631`：第二张复杂卡独立用例通过，耗时约 436 秒。第一轮确认天气为雨、阶段为“暗流涌动”，并提取全部五项资料；第二轮通过独立状态确认补回写，第一轮资料保持原样，最终磁盘恢复一致。合计两轮正文、三次模型请求。
- 最终联合运行：`1788580253208`（魔法少女）、`1788580369848`（医生）、`1788580572221`（岁寒新正）全部通过。分别使用 1、2、4 次模型请求，合计 77680 个服务端报告 token，包含思考与输入；不等同于计费额度。岁寒新正最终天气为雨、好感为 2、剧情事件未解锁、阶段仍为“暗流涌动”，两个历史资料面板与磁盘恢复均通过。

最后一次岁寒新正的两轮正文都需要补做状态确认。此前原始响应已观察到旧卡要求的 `delta` 操作仍被模型输出，尽管当前白名单要求 `replace`。运行时拒绝整批非白名单更新，再由一次受限请求生成合法确认；没有直接执行未知操作。这保住了本次状态，但带来了额外时延，不能称作完整的旧协议接管。

早期 Flash 实测和一次 Pro 实测出现只有思考、没有正文。其中 Pro 一次输出／思考 token 均为 2580，远低于 32768 的上限，因此不能简单归因为额度不足。该失败发生在原始 SSE 记录加入之前，尚不能据此确定是服务端输出还是协议转换问题。后续成功样本同时包含正文 delta 和最终 message，客户端能够正常接收。没有通过自动重试把失败隐藏成成功。

测试也修正了一个假阳性：最后一条用户消息的 COMPLETE 状态不能代表模型成功。现在必须存在真实生成的助手回复、有正文、状态完成；复杂卡另检查状态确认、玩法事实与恢复结果。

## 后续应验证的方向

下一步应先审计实测中反复出现的有限增量操作，减少原卡协议与白名单之间的差异及额外确认请求。同时拿未参与实现的新卡，重复“列出原始行为 → 映射到已有能力 → 标出缺口 → 验证具体玩法”，检验能力是否可复用，再建设自动适配生成。自动生成的候选仍须通过相同校验与行为验收。

真正需要扩充的应是已被多个样本证实的领域能力；不要为提高支持率重新建立通用 JS 宿主，也不要让模型任意生成操作链。长剧情、动态世界书条件和更复杂的集合更新仍需要后续实践，不能由本次结果代替。
