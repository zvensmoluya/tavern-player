# 扩展依赖与原生图像能力初查

日期：2026-09-08。状态：研究记录与候选方向，尚未修改产品能力或发起模型编译。用户要求核查社区所称“酒馆助手／提示词助手”，并检查新加入 source 的图像依赖样本。

## 两种扩展与已有覆盖

- 酒馆助手为 Tavern Helper（N0VI028/JS-Slash-Runner）。提供 HTML/CSS/JS 界面、脚本、变量、世界书操作、生成控制、事件及消息操作等宿主接口。作者可以基于这些接口构建玩法，它不只是界面美化或统一体验设置。[官方说明](https://n0vi028.github.io/JS-Slash-Runner-Doc/)
- “提示词助手”不是本轮确认的正式名称；在这种并列语境下，很可能指 ST-Prompt-Template，其 manifest 名为 Prompt Template/提示词模板。它在发送／渲染阶段处理 EJS、条件、变量和提示词注入。具体作者用词仍应依据插件链接确认。[官方仓库](https://github.com/zonde306/ST-Prompt-Template)、[manifest](https://github.com/zonde306/ST-Prompt-Template/blob/main/manifest.json)
- 本项目已经研究这两个方向，并实现原 MVU、世界书 EJS 的只读子集和生成的 JS 原生 Surface。没有实现完整 Tavern Helper，也没有覆盖 Prompt Template 的所有处理阶段、共享作用域、写入或注入钩子。见 [EJS 接入](ejs-quickjs-integration-20260907.md)与[原生 Surface](native-script-surfaces-20260908.md)。
- 当前样本不足以计算社区采用率；常见于所选复杂卡不等于全部社区高频。依赖名称应落到具体调用、来源和运行阶段，不能用“安装了某扩展”作为等价兼容证明。

## C-06 源码盘点

原件 SHA-256：`8f24972a97e9cb357e105e5d7d101a7ec3b7ff5c6cc0f98a4024ac94a895583f`。通过 source 中原件哈希追溯；中间提取文件位于忽略目录 `build/image-card-research/`，不写入原卡和人物名称。

- 文件 1,249,548 bytes；PNG 含 chara 与 ccv3 两份文本元数据，选择 ccv3 解码为 V3。没有声明 `data.assets`。图像资源不是一套内嵌的 V3 资产清单。
- 有 20 个世界书条目、7 项启用 Regex、3 个助手脚本。脚本 0 为启用的 MVU 引用，脚本 1 为停用旧 Schema，脚本 2 为启用 Schema。20 项世界书未出现 EJS 标签；这张卡不能用来验证 Prompt Template 兼容。
- 解码后的 data 全树共 320 次 HTTP(S) 字符串引用，去重 107 个。其中图床地址 102 个：按后缀分类为 100 个图片候选（85 PNG、14 JPG、1 WebP）和 2 个 TTF 字体。另 5 个地址为脚本／样式依赖。只核查字符串，没有请求文件，未验证 MIME、内容、大小或可用性。
- 世界书条目 9 停用，包含 102 次链接出现；它是素材备忘录，不能被强制启用或当作运行来源。相关资源也由启用 Regex 独立引用；本轮没有靠停用条目赋予执行权。
- Regex 3 与 6 的替换内容完全相同，约 40.6K 字符，但触发标记不同；不能把两个触发行为直接去重。两者含 Vue 界面、图像映射、MVU 读取与更新事件监听。Regex 4、5 另含开场介绍界面与图片。

## 图像在体验中的实际作用

启用界面源码显示：角色列表从 MVU `stat_data.characters` 读取人物及状态，通过键名映射选择头像；点击条目进入详情，选择图片并显示状态。图片选择使用候选数组和随机数，点击还会切换展示及重新选择；没有证据将这种选择解释为按好感度自动换图。未配置图片时有文本占位。原界面挂载时预加载数组中的资源，并监听 MVU 初始化／更新刷新状态。

这说明资源链路需要同时考虑“取得哪个文件”和“何时选择、切换、恢复哪个文件”。仅支持 Markdown URL 或下载图片不足以恢复原行为。本次只分析程序结构与资源引用，未下载或展示图库，未执行源 HTML 或远程脚本。

## 现有能力的具体缺口

| 环节 | 当前实现 | 研究问题 |
| --- | --- | --- |
| 本地静态图 | CharacterRepository 管理本地资产，固定 NativeSceneView 通过状态值选择 assetId，Compose 有界解码 | 如何接入来自外部引用、最终可复用的资源 |
| 远程图 | 导入保留 URI，提示不抓取；编译指令明确不支持 | 下载时机、按需加载、去重、失败重试、缓存与离线行为 |
| 动态图片 Surface | NativeSurfaceData 虽有 scene 类型，但数据结构没有图片或 assetId 字段；collection 条目同样没有缩略图 | 高层图片展示与列表缩略图的最小表达 |
| 选图与操作 | JS 可计算并保存 programState，宿主能随操作重投影 | 随机选图是临时界面状态还是可恢复操作结果，应明确而非每次 present 重抽 |
| 来源关联 | 编译看到启用源码与本地 assetIds，无远程资源登记流程 | 模型声明原始来源引用，宿主核对后登记资源；不要让模型编写图片内容或任意替换 URL |

远程图片此前是明确延期项，不是完全未考虑图片；但动态 JS Surface 对图像的表达确实尚未建立。

## 建议的下一步研究

先使用中性的头像／场景夹具验证一条完整链路：来源图片引用 → 稳定资源标识 → 宿主按需取得并校验图片 → 原生列表／详情呈现 → 操作选择与状态恢复。资源获取由宿主管理，JS 只引用资源和计算展示结果；不需要为此开放任意脚本网络访问或把整个 DOM 搬入 App。

优先比较图片 Surface 与 collection 缩略图的组合是否足够，再决定是否需要画廊。缓存文件生命周期与候选分支状态分别建模：同一个文件可复用，分支选择结果需要可追溯。中性夹具覆盖断网、重复 URL、失效资源、未知人物键、重新投影不意外重抽，以及进程恢复。原界面的字体、CSS 框架与整体布局独立评估，不与图片支持绑定交付。

本轮未运行网络资源探测、模型编译、App 测试或设备验收；这是一份源码调查，不是 C-06 兼容结果。没有改变既有“远程图片延期”实现边界，后续实现应以明确的新决定更新相关文档。

## C-07：手机编译失败与助手容器提取遗漏

2026-09-09 后续：已确认上游接受键值对数组，并修复本地容器提取；世界书读取 MVU 状态的已有链路与宏格式差异见[后续实现记录](helper-world-book-state-read-20260909.md)。下文保留昨晚调查时的结论，不代表后续模型编译或手机验收已通过。

同日用户报告另一张卡在手机“准备游玩”时失败，提示初始值与定义不匹配。原件 SHA-256 为 `0166ea69a6bdfa0e7559cc98e877d3d5b6b106bc12e1c712a45ba96585f359f0`，文件 1,032,388 bytes。源码提取材料保留在忽略目录 `build/template-card-research/`；通过 source 原件哈希追溯。

已确认该文件的 `data.extensions.tavern_helper` 为键值对数组，而非提取器当前接受的对象：

```json
[
  ["scripts", [{"type": "script", "enabled": true, "content": "…"}]],
  ["variables", {}]
]
```

以上为缩略结构示意。原件实际有两个启用脚本，其中一个注册 MVU Schema，另一个引用 MVU；助手 variables 为空对象。解码后的 data 全树没有 EJS `<%` 标签，也没有 `ST-Prompt-Template` 或“提示词模板”字面引用，因此目前明确证据是 MVU／酒馆助手依赖，不能凭用户对插件名称的推测判定它是 EJS 执行故障。

`NativeProgramExtractor` 将 `extensions["tavern_helper"]` 直接转换为 `JsonObject`，数组得到 null，后续 scripts 提取和 helper metadata 收集均不执行。同时 `tavern_helper` 又被排除在未知扩展告警之外，因此两个启用脚本静默遗漏，原 Schema 未进入模型输入或可引用来源。这是已通过原件结构与代码路径确认的缺口，不是模型对完整源码的理解失败。

用户描述对应 `NativeAdaptationValidator` 的 `STATE_TYPE_MISMATCH`，报错原文为“初始值与状态类型或字段定义不匹配”，路径是 `state[index].initialValue`。它检查 Player 状态：标量必须符合声明类型，Record 字段集合和标量字段类型必须匹配，Collection 各行必须符合字段定义。它不是 MVU 初始化时的 Schema 异常。

合理但尚未完整证实的失败链路是：助手容器遗漏 → 模型看不到 MVU Schema 并选择 Player 分支 → 生成的状态初值与字段定义不一致 → 本地拒绝安装。手机 `CharacterLibraryViewModel` 当前只显示前三项 issue 的 message，没有保存失败的模型响应、路由结果或完整字段路径。本轮没有那次原始响应，不能定位具体生成错误的字段，也不能把上述推断写成已重放的结果。

后续工作记录：

1. 用中性夹具覆盖对象与键值对数组两种助手容器，保留原始来源路径及启用状态；这是容器格式兼容，不是新增按卡名或 JS 写法识别状态来源。
2. 对不支持或畸形的助手结构明确报告，避免在材料缺失时继续宣称已提供完整程序。重复键、非字符串键等情况需要定义行为，不应随意转换丢失内容。
3. 研究保存失败诊断的最小范围，至少能够关联路由、错误 code/path 和编译版本；当前缺少这些记录限制了手机故障复现。
4. 完成通用提取修复后，再验证提供给模型的来源；不得通过放宽初值类型校验、修改原 Schema 或补写模型答案绕过失败。
