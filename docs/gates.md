# Tavern Player GATE

> 工作草案：用可验证的阶段门，控制一个“社区内容编译器 + 原生运行时”项目的范围。

## 目的

Tavern Player 的核心问题不是先做多少聊天页面，而是证明我们能把 SillyTavern 社区长期形成的角色卡、世界书、Regex、Preset 和约定，编译成一个稳定、可诊断的运行时。

因此，工时只是 timebox，不是通过条件。每个 GATE 都必须留下可复现的证据；没有证据，就没有通过。

核心链路暂定为：

```text
社区来源
  -> 解析 Parsed Source
  -> 归一化 Content IR
  -> 编译 Execution Plan
  -> 运行时组装 Provider Request
  -> 接收 Provider Response
  -> 后处理并渲染用户消息
```

## 通用规则

- 每个阶段都必须有一个真实或接近真实的 fixture，而不是只用手写的最小对象。
- 核心编译器和运行时优先保持为不依赖 Compose 的 Kotlin 代码，以便用 JVM 测试验证。
- 不允许静默丢弃已声明支持的内容；暂不支持的内容必须产生明确诊断。
- 已知的 Sev-1 问题不能带入下一关。`CONDITIONAL` 只能用于不影响核心链路的已记录问题。
- 阶段结束时做一次 `PASS`、`CONDITIONAL` 或 `STOP` 决定，并记录未覆盖的风险。

每个 GATE 的固定输出：

1. 可运行的最小实现或原型。
2. 固定 fixture 和可重复的验证命令。
3. 支持、部分支持和不支持的内容清单。
4. 未解决风险，以及下一阶段明确不做的事项。

## 编译器不变量

这四条是所有阶段共享的技术门槛。它们决定 Tavern Player 是一个内容运行时，而不是把社区格式硬编码进页面的适配器集合。

- **语义不静默丢失**：已声明支持的字段必须进入 IR 或产生诊断；未知字段不能假装已经执行。
- **来源可追溯**：IR 和诊断应能指出内容来自哪个文件、字段或规则，方便解释兼容性问题。
- **顺序显式**：角色设定、示例对话、世界书、Preset、宏和 Regex 的执行阶段与优先级必须体现在 `Execution Plan` 中，不能依赖调用顺序的副作用。
- **结果确定性**：同一来源、配置和输入上下文应生成相同的 IR、执行计划和 mock 请求；需要时间、随机数或网络状态时，必须由运行时显式注入。

这四条不要求 M0 一次解决所有 SillyTavern 语义，但要求每个暂未实现的语义都有明确的状态和边界。

## M0：可行性

**Timebox：8–12h**

### 目标

证明“内容可以被编译并跑完一轮对话”，同时尽早暴露格式和架构上的致命误判。

### 必须完成

- 读取一个接近真实的 SillyTavern 角色卡 fixture，至少覆盖角色设定、示例对话和一个可执行规则。
- 将来源归一化为稳定的 `Content IR`，并生成可检查的 `Execution Plan`。
- 跑通一轮完整链路：角色内容 -> Prompt/Provider 请求 -> mock 响应 -> Regex 或等价后处理 -> 最终消息。
- 至少验证一个世界书条目的触发和注入顺序。
- 至少验证一个 Regex 后处理规则。
- 对不支持或格式错误的输入返回结构化诊断，不因单个字段导致崩溃。
- 编译器和运行时可以在 JVM 测试中独立验证，不依赖 Android UI。

### 通过证据

- `./gradlew test` 或等价的仓库内命令可以从干净环境重复通过。
- fixture 的输入、归一化结果、生成的请求和最终输出都有 snapshot 或断言。
- 同一输入在相同配置下生成确定性的执行计划。
- 至少有一个失败 fixture，能证明错误会被报告而不是静默降级。

### 刻意不做

生产级聊天 UI、账号体系、真实 Provider 接入、流式输出、完整格式兼容、数据迁移和性能优化。

### 失败条件

如果无法在 timebox 内稳定表达 `Source -> IR -> Plan -> Runtime`，或必须把 Compose/Android 组件塞进核心逻辑，M0 应判定为 `STOP`，先重新收敛 IR 和运行时边界。

## M1：首板

**Timebox：25–40h**

### 目标

做出可以安装、导入角色、选择基本配置并完成真实对话的 Android 客户端。

### 必须完成

- 从文件或分享入口导入首个确定支持范围内的角色卡格式，并保留角色头像和主要元数据。
- 本地持久化角色、会话和必要的编译产物；冷启动后数据仍可用。
- 提供角色库、角色详情和聊天三个核心界面。
- 接入一个明确选定的 Provider 协议，包含超时、取消和可恢复的错误状态。
- 支持默认 Preset，以及在开始会话时选择 Model/连接配置。
- 聊天消息经过同一套编译器和运行时，不允许 UI 另写一套 Prompt 拼接逻辑。
- 至少覆盖发送、重新尝试和会话恢复这几个日用动作。

### 通过证据

- 在模拟器或真机上，从全新安装开始完成：导入 fixture -> 打开详情 -> 发出请求 -> 收到回复 -> 关闭并重新打开应用。
- 网络错误、解析错误和空响应都有可理解的界面状态，应用不崩溃。
- 核心 JVM 测试和 Android 基础构建均通过。
- 首板支持范围写成清单，未支持内容在导入时可见地提示。

### 刻意不做

世界书编辑器、Regex 编辑器、Preset IDE、插件系统、TTS、生图、长期记忆和多 Provider 的完整管理后台。

## M2：兼容 Alpha

**Timebox：30–60h**

### 目标

吃掉主流 SillyTavern 内容，而不是追求功能列表上的“全兼容”。

### 必须完成

- 建立来自真实社区内容的兼容性 fixture corpus，覆盖主流角色卡版本、PNG/JSON 来源、世界书、Preset、Regex 和常见宏/占位符。
- 每种能力有明确状态：`supported`、`partial` 或 `unsupported`，并有对应诊断。
- 对角色卡、世界书、Preset 和 Regex 的关键执行顺序建立 golden tests。
- 长上下文、多个世界书条目和规则冲突有可重复的测试结果。
- 导入失败、部分兼容和降级行为不会静默发生。
- 兼容性测试不依赖网络 Provider，可用固定 mock 请求验证编译结果。

### 通过证据

- corpus 中的所有 fixture 都能被安全读取；核心支持项有 golden 输出。
- 发现不兼容时，能指出来源、阶段和原因，而不是只显示“解析失败”。
- 新增一个 fixture 后，可以在单条命令中加入回归套件。
- Alpha 版本的已知限制和迁移建议可以被用户查阅。

### 刻意不做

复制 SillyTavern 全部设置页、追逐每个插件、承诺与其内部实现逐字节一致，或为兼容性引入无法解释的特殊分支。

## M3：公测打磨

**Timebox：30–60h**

### 目标

让已有兼容能力变成可长期使用、可恢复、可发布的 Android 产品。

### 必须完成

- 数据库/文件格式版本化，包含升级、备份和导出路径。
- 凭据使用 Android 安全存储；日志和诊断不泄露密钥或完整私密对话。
- 覆盖主要生命周期：后台恢复、进程被杀后恢复、旋转/窗口变化和网络切换。
- 对长上下文、失败重试和流式响应做资源与性能检查。
- 完成无障碍、基础本地化、空状态、错误状态和导入反馈。
- 建立发布构建、回归测试、崩溃收集和已知问题清单。

### 通过证据

- Release candidate 在目标 Android 版本和至少一台真实设备上完成核心流程回归。
- 不存在阻断安装、导入、发消息或恢复会话的 Sev-0/Sev-1 问题。
- 从 M1/M2 的 fixture corpus 到发布构建有自动化回归路径。
- 公测说明明确支持范围、隐私边界、数据备份方式和已知限制。

### 刻意不做

在没有证据的情况下继续扩张功能面，或把公测当成完整 SillyTavern 替代品的承诺。

## 首个 GATE 评审问题

在开始 M0 前，只需要先回答四件事：

1. 首个 fixture 采用哪一种角色卡版本和来源形式。
2. `Content IR` 的最小字段集合是什么。
3. Prompt 编译和后处理的执行顺序如何被测试固定下来。
4. M0 使用哪一个 mock Provider 请求作为可观察输出。

这四件事确定后，M0 才能真正作为 8–12 小时的可行性实验，而不是提前实现半个播放器。
